# Task Packet — 2026-09-22-generated-artifact-governance

## 背景

`NAMING_AND_BOUNDARIES_REMEDIATION_PLAN_2026-09-22.md` Wave 1 第 4 项。审查发现：

生成源、生成产物与手工层没有明确区分，生成产物没有稳定标记，也没有专门的漂移门禁

（只有清理 smoke 残留的 `check:generated-modules`）。生成文件被手工改动后无法被发现。

## 目标与交付物

1. **稳定生成标记**：`Code generated by pantheon low-code generator. DO NOT EDIT.`
   - 唯一来源：`frontend/scripts/cleanup-generated-modules.mjs` 的 `GENERATED_MARKER` +
     `markTemplate()`；4 个注册表模板与 i18n 模板统一带上首行标记。
   - 已落到 11 个在库生成产物（2 个 Go 注册表、3 个前端注册表、5 个 i18n fallback，
     外加 `frontend/src/modules/generated/system.ts`）。
   - JSON 产物（`schema/generated/feature-ledger.json`）不能注释，按路径 + 可解析性识别。
2. **漂移门禁**：`scripts/harness/check-generated.mjs`
   - 校验 11 个带标记产物的首行标记与存在性，外加 1 个 JSON 产物的可解析性。
   - 规则：`generated-artifact-missing` / `generated-marker-missing` /
     `generated-marker-not-first-line` / `generated-artifact-invalid`。
   - npm script `check:generated`；`.github/workflows/quality.yml` 新增阻塞步骤
     “Check generated artifacts”。
3. **所有权文档**：`docs/designs/REPOSITORY_LAYOUT.md §7` 更新——生成源（`system_module_registration`
   + `schema/generated/**.json`）、生成产物清单、手工维护层（`business/*` 内非生成路径）、
   标记与漂移检查。§10.1 增加 `check:generated` 映射。
4. **测试**：`tests/scripts/harness-check-generated.test.mjs`（6 例）。

## 边界

- 层级：platform / governance（低风险）→ L1。
- **不改低代码业务能力**：不改生成器产出的模块结构、不改 `system_module_registration`
  写入逻辑、不改 i18n 运行时。
- 不删除 `check:generated-modules`（仍负责 smoke 残留清理），不接入旧的
  `check-arch-boundaries.mjs`（属后续 ratchet）。

## 评审视角（Reviewer 检查点）

- [x] 标记是否真的会被生成器保留？——标记同时进 `REGISTRY_TEMPLATES` 与在库产物；
      `cleanup` 优先从 git index 恢复（含标记），模板为未跟踪回退。
- [x] 是否误判合法的“已生成模块”状态？——否；门禁只校验标记与存在性，不要求注册表为空
      （真实生成模块会合法地填充注册表）。
- [x] 是否改变低代码能力？——否，纯治理/门禁。
- [x] JSON 产物如何处理？——不能注释，改为按路径 + `JSON.parse` 识别，并在文档写明。

## 残余 gap（显式）

- 生成器（`backend/modules/lowcode/generator`）在产出新模块文件时尚未自动写入标记；
  当前门禁只覆盖稳定的固定产物。让生成器对每个新产出文件写标记属后续 ratchet。
- 旧的 `check-arch-boundaries.mjs`（`checkGeneratedRegistry`）未接入 CI，与
  `check-generated.mjs` 职责部分重叠。

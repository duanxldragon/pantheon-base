# Task Packet: 2026-10-12-v0161-release-cut

## Goal

把 v0.16.0 tag 之后合入 main 的两项改动（#377 主干偶发失败根因修复、#380 发布产物门禁）打包为一次
**patch** foundation release（v0.16.1），并——与 v0.14.0/v0.15.0/v0.16.0 不同——**发布四件可消费产物**，
使 `pantheon-ops` 的 consumer lock 真正能够推进。

由于发布脚本依赖 `git`/`tar`/`gh` 子进程，而准备本改动的主机无法 spawn 任何子进程，本次发布由新增的
`Foundation Release Cut` workflow 在具备这些工具的 runner 上执行。本次发布零消费侧接口变更。

platform

## Implementation Notes

- 版本判定先行：`docs/VERSION_MANAGEMENT_GUIDE.md` §2.4 的 patch 覆盖「Bug 修复（不改变功能行为）」，
  #377 正是此类；#380 是门禁增强但单独不足以发 minor（§2.3 的「质量门禁增强」指新增能力模块级别，
  本处为修复既有缺口）。故本次为 **patch（0.16.1）**。
- 消费侧零影响：#377 的缺陷只在测试夹具路径可达（`testmysql.Open` 在 `t.Cleanup` 里 DROP 测试库，
  使池不可达从而地址被复用），生产恒传进程级单例池；#380 只新增门禁。无路由、权限码、菜单 seed、
  i18n key 或契约形状变动。
- **本次刻意反转 v0.16.0 的产物决策**：v0.16.0 收口包记录「v0.15.0 的 Release 无 assets，故 v0.16.0
  照抄：tag + 正文」。但 `pantheon-ops` 依赖 `repo.tar` + bundle 归档做 SHA-256 校验后物化，无 assets
  即不可消费——这正是 lock 卡在 `pantheon-base-v0.13.0` 的直接原因。故 v0.16.1 必须发布四件产物。
- 发布必须走 CI：本机 Node 无法 spawn（`spawnSync` 对 git/gh/tar/node/echo 均返回 `EBUSY`，关闭沙箱后
  复测一致），而 `build-release-bundle.mjs` 与 `publish-foundation-release.mjs` 均依赖 spawn。
- 不放松既有门禁：`publish-foundation-release.mjs` 自身会校验干净工作树、目标 commit 上的
  `Release Gate Summary` 必须 success、manifest `baseCommit` 必须等于目标 commit、四件产物校验和、
  发布说明非占位、tag 不存在或指向同一 commit，且**拒绝覆盖已存在的 GitHub Release**。
